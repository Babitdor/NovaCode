Fix verdicts being stored under an unreachable key; measure against real Tev1

VerdictCandidate carried only `content_chars`, so the scorer stored each verdict
against a synthetic placeholder. The cache is keyed on the result's content
(`result_key`), so verdicts landed under a key no real ToolMessage can produce:
0 of 149 results could be answered for, every lookup missed, and the edit failed
open (kept everything) at every threshold. The fail-open design did exactly what
it promises; it was never able to answer.

Carry the real content on the candidate and store/look up with it. Add a
regression test with irregular payloads, mutation-checked: a payload of
"x" * 100 cannot express this defect at all, because "x" * content_chars
reproduces it exactly, which is how an earlier version of the test passed with
the defect re-injected.

Measured against Ollama 0.35.0 + tev1:0.8b over the 6 real sessions that have
more than 5 tool results:

  heuristic (keep=5): cleared 859, regretted 170, 1,010,187 chars, 0.17 /1k
  verdicts @ 0.80   : cleared  49, regretted   8,    18,364 chars, 0.44 /1k
  verdicts @ 0.70   : cleared  43, regretted   8,    15,663 chars, 0.51 /1k

The heuristic wins on both axes at every threshold, so the plan's Phase 5 gate
(not worse regret at matched tokens reclaimed) fails and the feature is not
promoted. Every noul observed fell in 0.51-0.76 (n=70): the model never commits
to a verdict, so a threshold inside the band clears almost nothing and one above
it clears everything at once.

Also included: the ported scorer, VerdictToolUsesEdit, the capacity probes, and
the measurement harness (self-checked to reproduce the production reducer
exactly). None of it is wired into the agent or merged.
