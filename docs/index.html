nova ❯man nova

A coding agent that verifies its own work.

NovaCode is an open-source, terminal-based AI coding assistant built on LangGraph and the deepagents framework. It runs entirely in your terminal with a Textual TUI, a headless non-interactive mode for scripting and CI, and remote bridges for Discord and Telegram.

Version 1.0.23 · MIT licensed · Python 3.11+. Runs locally, brings your own model. NovaCode does not retrain your model. What changes are prompts, skills, and thresholds on disk, readable and deletable.

  • ~30 core tools · ~85 total
  • 12 async background agents
  • 8 model providers
  • 20 MCP presets
  • 7 sandbox providers
  • 50+ built-in skills

Core flow

User Input → CLI Entry (main.py) → Agent Loop (core/agent_loop.py) → UI Renderer

  1. CLI Entry

    main.py to cli_main(): parses args, initializes SessionState, runs optional onboarding, then enters the TUI or the headless runner.

  2. Agent Loop

    core/agent_loop.py to iterate_agent_events(): the single canonical async generator driving the LangGraph agent stream.

  3. UI Events

    ui_events.py: dataclass instances decoupled from rendering. The TUI, headless runner, and remote bridges all consume the same event types.

  4. Middleware

    Wraps every model call: retry, vision, learning, security, bootstrap, steering, file tracking, loop guard, rubric, context editing, shell, memory, task discipline.

Key design principles

One canonical agent loop

iterate_agent_events() drives a LangGraph agent stream and yields ui_events dataclasses. Bug fixes and features belong here so every renderer benefits.

SessionState is a composite

Six state slices (UISettings, AgentRuntimeState, RemoteBridgeState, BackgroundTaskState, NotificationState, WikiState) with properties that delegate to slices. Zero callers change when a slice is added.

Deepagents is monkey-patched

Three patches at import time: validate_path (Windows path normalization), perform_string_replacement (UTF-8 BOM tolerance), and create_sub_agent (graph compile caching).

Heavy imports are blocked

A meta-path finder makes import transformers/torch raise ImportError (305 MB / ~13 s to 145 MB / ~2.4 s). Set NOVA_ALLOW_TRANSFORMERS=1 to opt out.

Verify installation

verify.sh
nova --version
nova doctor          # validate config + connections
nova               # start the TUI

nova doctor runs six checks: configuration file, secrets, LLM provider connection, Tavily connection, file permissions, and the voice stack. It returns exit code 0 when everything passes.

Update Nova

nova update --check  # check without installing
nova update          # update the running installation

The TUI checks in the background at startup and hourly. Installation detection covers source checkout, uv-tool, git, and package installs. On Windows, uv-managed updates run in a separate detached process because nova.exe locks the package directory. Set NOVA_DISABLE_UPDATE_CHECK=1 to disable background checks.

Onboarding

First-run setup checks what you enter before saving it: an API key is tested against the provider, and an Ollama host must answer with a model installed. Keys go to the OS keychain. A typo shows up on the setup screen, not on your first prompt.

Credential storage

Keys go to the OS keychain (via the keyring library) with a permission-restricted JSON fallback. The endpoint and project are paired with the key as non-secret metadata in Nova.config.json. Enumeration and deletion are supported, and secrets are never logged or interpolated into exception messages.

nova secrets set openai_api_key
nova secrets set anthropic_api_key
nova secrets list
nova secrets delete openai_api_key

get_provider_auth_status() resolves credential readiness into a ProviderAuthStatus with states: CONFIGURED, MISSING, NOT_REQUIRED, MANAGED, UNKNOWN.

nova ❯nova -p "..."

Headless mode.

Run a single prompt non-interactively and exit. Built for scripting and CI.

headless.sh
# Basic: run a prompt, print the response
uv run nova -p "summarize the changes in this repo"

# JSON output, capped at 10 turns, approvals denied
uv run nova -p "run the test suite and report failures" \
  --output-format json \
  --max-turns 10 \
  --deny-tools

# Stream JSON events
uv run nova -p "explain the architecture" --output-format stream-json

# Pipe the prompt on stdin
echo "explain src/main.py" | uv run nova -p

Runner behavior

headless/runner.py drives a single prompt through the UI-agnostic event stream (iterate_agent_events) to completion with no human present.

  • prompt from headless_prompt, format from headless_output_format
  • tool interrupts use evaluate_tool_actions unless --deny-tools
  • a None verdict (ask the user) is converted to an approve
  • question/plan interrupts resolve to the default response
  • counts turns, accumulates text, tracks usage, enforces max-turns
  • autosaves the run as a resumable session; never fails on a save error

Headless runs are the exception to the approval rule: --deny-tools rejects everything, so a pipeline fails closed instead of hanging on a prompt nobody is there to answer.

Tool search

Only core tools are bound to the model on every call. search_tools finds the rest on demand. Search covers every currently available tool, including core and already loaded tools, plus specialist subagents. Use a capability description, an exact name, a partial name, or a wildcard.

MCP tools (serena, playwright, cua-driver, etc.) are discovered by MCPMiddleware and attached to the main agent. They are granted to subagents selectively via MCP_TOOLS_BY_SUBAGENT.

nova ❯memory_search

Memory system.

A three-tier model: Episodic, Semantic, and Procedural.

The three tiers

Episodic

hermes/tracker.py: the durable, time-ordered record of what the agent actually did. Tool history, counters, per-tool stats, and per-skill effectiveness. Stored in the durable store at ~/.nova/store.db.

Semantic

agent.md (user model), memories/INDEX.md (topic pointers), memories/<topic>.md (topic facts), and HABITS.md. Files are written newest-first and compacted past 12,000 chars.

Procedural

Skills are the procedural memory: reusable workflows the agent can invoke. Created and refined by Hermes, stored in ~/.nova/skills/.

Durable store

A single sync SqliteStore at ~/.nova/store.db (with a stdlib-sqlite3 fallback), wrapped by a DualModeStore for both sync and async access. All Hermes namespaces live under the ("nova", ...) prefix.

AgentMemoryMiddleware

  • loads memory into the system prompt at before_agent
  • always injects agent.md, memories/INDEX.md, HABITS.md, learning overview
  • per-turn retrieval: lexical overlap scoring, top-3 topic bodies
  • hot-reloads memory files when they change on disk
  • prompt-cache split: the retrieval block sits after the cache breakpoint

nova ❯/skills

Skills system.

50+ built-in skills with progressive disclosure. Install from any public GitHub repo.

A skill is a playbook (SKILL.md) with YAML frontmatter (name, description required; version, tags optional) and a Markdown body with canonical sections: When to Use, Quick Reference, Procedure, Pitfalls, Verification. Optional supporting files, scripts, and even an executable skill.py entry point can ship alongside.

Skill loading

Skills are loaded from multiple sources in precedence order (later overrides earlier):

  1. User skills

    ~/.nova/skills/

  2. Shared global

    ~/.agents/skills/

  3. Claude skills

    ~/.claude/skills/

  4. Plugin skills

    ~/.nova/plugins/<name>/skills/

  5. Project skills

    .agents/skills/, .nova/skills/, .claude/skills/

Caching uses a directory signature (name, mtime, size) per skill, so only changed directories are re-parsed. A disk cache at ~/.nova/cache/skill_index.json enables cross-process reuse.

Skill retrieval

Hybrid search fuses BM25 (exact terms) with static Model2Vec embeddings (paraphrases) by reciprocal rank. The embedding model is minishlab/potion-code-16M.

FunctionBehavior
search(query, k=5)Top-k skills
suggest(query, k=3)Skills that stand out (z-score ≥ 4.5, cosine ≥ 0.4)

RefreshingSkillsMiddleware is tiered:

TierBehavior
ListingOnly most-used skills within a char budget (1% of window)
SuggestionsEach new user message matched against the whole library; top picks added as Internal context
skills_searchA tool for needs that surface mid-task

nova ❯/learning

Autonomous learning.

Hermes is Nova's learning and memory subsystem. It runs out-of-band and never blocks the agent's task turn.

The system is orchestrated by NovaLearningMiddleware (hermes/middleware.py), a thin orchestrator that delegates to four focused modules:

ToolUsageTracker

Episodic tier: counter, tool history, skill stats.

ReviewRunner

Periodic review lifecycle: trigger, OOB invoke, content persistence.

SkillManager

Skill lifecycle: create, cleanup, refine.

EvolutionEngine

Task-completion skill evolution.

The review loop

Trigger logic (hermes/review.py, ReviewRunner.should_review()). A review fires when any of these hold (and a review wasn't just done):

  • Failure burst: ≥ FAILURE_BURST (default 3) failed tool calls in the current window
  • Substantive threshold: count ≥ REVIEW_THRESHOLD (default 10) AND the window contains real work
  • Hard cap: count ≥ 2× threshold (so all-trivial windows can't defer forever)
  • Clean win: real substantive work, zero failures, past the floor

OOB model invocation: the review runs as a separate, out-of-band model call — it is NEVER injected into the agent's task turn.

Content persistence: after the OOB review, the parsed content is applied:

Review outputApplied to
<user_model> blocksagent.md
<lesson topic="..."> blocksmemories/<topic>.md + INDEX pointer
<habit> blocksHABITS.md

Post-review actions: every review runs cleanup_legacy_skills_once() and maybe_create_from_review(); every 5th review runs maybe_refine_skills() (one high-failure skill per cycle); every 10th review runs maybe_curate(), ThresholdTuner.run_tuning_pass(), and PromptEvolutionEngine.maybe_auto_evolve().

What Hermes learns

  1. User model

    User preferences, communication style, merged into agent.md.

  2. Topic lessons

    Cross-session facts/lessons organized by topic.

  3. Good habits

    Reusable practices that worked well, stored in HABITS.md.

  4. Skills

    Episode-grounded skills created from review <skill> blocks.

  5. Prompt templates

    A/B-tested rewrites of system prompt templates.

  6. Verification memory

    Per-repo failure patterns that make the inline verifier smarter.

Self-evolution engine

Fires at task completion:

  1. Slice

    The task's episodic window.

  2. Score

    Complexity via a deterministic heuristic (no LLM).

  3. Invoke

    If complex enough (≥ 8), runs an OOB model call returning <skill> (new) or <level_up skill="name"> (improvement).

  4. Debate

    New skills go through one adversarial critic round before freezing.

Loop engineering enhancements

EnhancementModuleWhat it does
Inline Verification Loopcore/verification_loop.py, hermes/verifier.pyAfter each task, an OOB LLM call grades the output against a rubric. On a failing verdict, the agent is re-driven with feedback (up to 3 retries). Fail-open by design.
Prompt-Template Hill Climbinghermes/prompt_evolution.pyProposes targeted .jinja rewrites, A/B tests them using verifier pass/fail as the quality signal, and promotes or discards. Packaged templates are never modified — overrides live in ~/.nova/prompt_history/.
Cron / Heartbeat Schedulerremote/scheduler.py, commands/cron_handler.pyProactive scheduled tasks via standard 5-field cron expressions.
Threshold Auto-Tunerhermes/tuner.pyNudges review-trigger thresholds toward the observed working style. Damped convergence (0.2 weight) with hard floor/ceiling bounds.
Webhook Ingress Serverremote/webhook_server.py, remote/webhook_adapters.pyExternal systems trigger a Nova run with per-source HMAC-SHA256 secrets.

Key design principles

  • Never block the turn: all learning runs OOB or in background tasks.
  • Fail-open: any learning failure logs and continues; never breaks the agent.
  • Durable persistence: all learning state survives restarts via the LangGraph BaseStore.
  • Bounded: every loop has hard caps (max retries, max lessons per review, etc.).

nova ❯/goal rubric

Verification loop.

Code written isn't the same as a task finished. Nova checks the result against what you asked for.

The loop

  1. Task

    The user's request.

  2. Understand

    Read the codebase, find the relevant code.

  3. Plan

    Decide what to change.

  4. Edit

    Write the code.

  5. Test

    Run the tests.

  6. Verify

    Grade the result. Fail? Back to plan.

When verification passes, the run is done, and the verdict and the diff that earned it are stored. When it fails, the failure comes back as feedback and the loop runs again, up to three attempts, then reports honestly instead of guessing.

Grader criteria

Five criteria scored by a separate model call:

  • responded to the request
  • wrote files
  • no errors
  • tests pass
  • did not modify tests to pass
CriterionWhat it means
Responded to requestDid the run address what the user actually asked for?
Wrote filesDid the run actually modify the codebase, or just talk about it?
No errorsDid the run complete without errors, exceptions, or failures?
Tests passDo the existing tests still pass after the changes?
Did not modify testsDid the run change the tests to make them pass instead of fixing the code?

Turning it on

# Grade each finished run (costs one extra model call per turn)
/learning on

# Hold a specific piece of work to your own criteria
/goal rubric <what counts as done>

Off by default. The inline verifier lives in core/verification_loop.py and hermes/verifier.py. It is fail-open by design: a verification failure never breaks the run.

Voice notes (Telegram)

Telegram accepts voice notes: they are transcribed with the configured /voice STT provider and sent to the agent as an ordinary prompt. The transcript is echoed back so you can see what was heard. In a Telegram forum, each session gets its own topic, and a question Nova asks you is deleted from the chat once you answer it.

Webhook ingress server

Let external systems (GitHub, Linear, or any signed sender) trigger a Nova run. Per-source HMAC-SHA256 secrets, timing-safe verification, binds to 127.0.0.1 by default. Manage with /webhook.

nova webhook list
nova webhook remove <name>

Streaming

Response chunks are captured from the agent's output and sent back to the originating platform. For Discord, messages longer than 2,000 characters are split. For Telegram the limit is 4,096. Edit-in-place streaming creates a single "live" reply message and edits it in place on subsequent calls.

FileContents

Four-tier persistence

  1. Checkpointer

    LangGraph, SQLite-backed. Persists message history per thread_id. Primary conversation state.

  2. Snapshot

    SessionManager's snapshot.json. The authoritative recovery generation, written atomically.

  3. Store

    Durable key/value at ~/.nova/store.db. SqliteStore, then stdlib fallback, then in-memory.

  4. Semantic files

    memory.md, workspace_state.json, ui_journal.jsonl, skills, worktrees, update cache.

Session lifecycle

  • saves the incoming prompt before execution
  • checkpoints active sessions every five seconds
  • saves again when a turn ends
  • resume with nova --continue or /sessions
  • abrupt termination can lose progress since the last save

Save is serialized via a @serialized_save decorator to prevent concurrent autosave and final-save interleaving. Restoration validates project root, repo hash, and NOVA.md checksum, but never blocks on a mismatch.

Parallel sessions

Parallel sessions run as separate OS processes, each bound to its own git worktree. The child streams ui_events dataclasses to the parent as JSONL; the parent decodes them back and feeds the existing TUI renderer. Up to four run concurrently.

DirectionMessages
Parent to childprompt, interrupt_reply, cancel, shutdown
Child to parentready, ev, interrupt, turn_done, error

Session leases are durable, TTL-based, and cross-process (DEFAULT_TTL = 300s, DEFAULT_RENEW_INTERVAL = 60s). On a lease conflict, a turn runs unleased rather than blocking. Worktrees live under ~/.nova/worktrees/<repo-name>/<slug>, outside the repo.

nova ❯/context

Context management.

A three-stage pipeline sized to the model's actual context window.

  1. Clear

    Older tool results are offloaded to /cleared/ so the agent can read them back.

  2. Compact

    The conversation is summarized hierarchically via LLM.

  3. Reserve

    A hard backstop always keeps an 8k-token reserve.

ContextManager

context/manager.py is a model-aware facade for all context-window operations:

MethodPurpose
window_size()Context window size in tokens
breakdown()Token breakdown against the window
model_config()Model configuration
budget()Process-global context budget
digest()Recent conversation digest

Compaction

Compaction rewrites the whole conversation into one synthetic HumanMessage carrying the summary. The pre-compaction transcript is archived to ~/.nova/sessions/<thread>/.

System One compaction (experimental) asks Jev or a compatible local/custom decision model whether each old tool result is still needed, and clears only results scored stale. Off by default. Configure through /model → Decisions to select Jev, Tev1, or Custom System One.

Context meter

The TUI's CTX meter uses the latest main-model input usage when available and an estimated summary/tail breakdown after compaction or resume. SESSION accumulates main-model input and output across tool-loop calls against a configured token budget (1M by default).

nova ❯open safe.book

Security & safety.

Autonomous doesn't mean uncontrolled. Every tool has a tier, and the tiers are yours to set.

Security middleware

security/middleware.py screens URL-bearing tool arguments for deception: hidden/invisible Unicode (BiDi overrides, zero-width chars, BOM), punycode domain spoofing (xn-- decoding), and mixed-script or confusable domain labels. Policy is warn and sanitize: invisible characters are stripped from the URL in place and the call proceeds; spoofing signals are surfaced as a notice but not blocked.

Human-in-the-loop

hitl/interrupts.py is a configurable interrupt system requiring user approval before destructive or external operations. 11 tool categories have schema-driven interrupt specs:

CategoryTools
Destructiveshell, execute, write_file, edit_file
Externalweb_search, fetch_url, http_request, browser_automate

Memorywrite_memory, create_memory_structure
User interactionask_question

File recovery

Automatic snapshots are taken before destructive operations. Files targeted by rm are captured before deletion, files overwritten by write_file have their previous content saved, and files modified by edit_file have the pre-edit content saved. Snapshots live in ~/.nova/trash/<session-id>/. Files over 10 MB are skipped. Restore via /restore or the list_trash and restore_file tools.

    ~/.nova/config.json exists and is valid JSON with a provider set.

  4. Tavily

    Tests the search API if a key is configured.

  5. Permissions

    Checks that secrets.json is not readable by others.

  6. Voice stack

    Checks audio imports, PortAudio, and the default input device.
